# Sync Strategies

## Grass Sync (DataManager — uploads/approvals/notes)
- **Incremental**: Start from last cached date minus 3-day safety buffer
- **Integrity check**: For past years, compare remote count vs local sum; force re-fetch on mismatch
- **Completion cache**: Mark past years as complete to skip future fetches
- **Batch**: 200 items/page, 5 concurrent pages, exponential backoff on 429/5xx

## User Analytics Sync (AnalyticsDataManager)
- **Quick Sync** (`quickSyncAllPosts`): For users with ≤1200 total posts. Sequential cursor-based pagination. Auto-triggered in `renderDashboard()`.
- **Full Sync** (`syncAllPosts` → `fetchPostsByCursor`): For large users. Resumes after `startId` and walks Danbooru's id cursor (`user:X`, `page=a<last id>`), one page at a time, committing each page as it lands. **Through v9.11 it used numbered pages** (`user:X order:id id:>N`, `page=1,2,…`) fetched by 5 workers with an in-order commit buffer: a numbered page is an OFFSET on the server, and in three full syncs of a 46k-upload account every edge 429 came on a page past 130 (T-209 measurements; T-210). A cursor page is an index seek at any depth, but needs the previous page's last id, so the walk is sequential: its speed is the server time per page. The run ends on an empty page only — a short page is not the end (the API may leave out posts the viewer cannot see). A page that does not move the cursor stops the run as incomplete instead of looping.
- **Page retries (v9.10)**: `classifySyncFetchError` sorts a failed page fetch into `rate-limit` (429), `transient` (5xx, the 30 s timeout abort, network `TypeError`, unparseable body) or `fatal` (other 4xx). The first two retry up to `SYNC_PAGE_MAX_ATTEMPTS` (5); `syncRetryDelayMs` waits out the shared rate limiter's remaining pause (`backoffRemainingMs()`) before each retry, so the request's 30 s timeout is not spent in a paused queue. Before v9.10 only 5xx retried, and one 429 stopped a 46k-post sync around page 210.
- **Resume gate (v9.10)**: `renderDashboard` decides "Data Synchronization Required" from the pre-check (`needsResumeSync`) before `fetchDashboardData`; only the Quick Sync path keeps the post-fetch check, since its pre-check numbers are stale.
- Both strategies store posts in IndexedDB and call `refreshCriticalStats()` to populate the piestats cache. Heavy tag distributions are deferred and freshen post-paint via `fetchDashboardData`'s SWR revalidate (v9.8.5).
- **Sync outcome (v9.8.7)**: `syncAllPosts` returns `SyncOutcome {complete}`. A page that exhausts its retries stops the run quietly, so the run resolves normally with only some pages committed; `complete: false` marks that. `finalizeSyncMetadata` then withholds the last-sync stamp and the backfill-complete flag (the stats refresh still runs), and the app-layer callers show a warn toast. Callers must not paint a success state on `complete: false`.
- **Overlap reconcile (v9.8.7)**: a post that has vanished from Danbooru's search entirely — expunged (permanently destroyed), or no longer credited to this uploader — never appears in the re-fetched window. *Deleted* posts are not in this group: Danbooru's default search includes them (verified 2026-10-29 with the sync's own `user:X order:id id:>N` query — no `status:` metatag — which returns `is_deleted: true` rows), so the re-fetch simply overwrites their row with the deleted flag. (The original v9.8.7 note claimed deleted posts were excluded; that premise was wrong, the prune itself is still correct.) After a **clean** run that committed at least one page, `pruneGhostPosts(uploaderId, startId, seenIds)` deletes this user's rows above `startId` that the remote did not return. Without it the stale row survives with `is_deleted:false` while survivors are renumbered, so its old `no` collides with a live post's (ambiguous `[uploader_id+no]` milestone lookups, local count drifting above remote). It runs *after* the fetch, not as a delete-then-refetch before it, so an interrupted sync can never leave a hole; a partial run is skipped because an unseen id may just be a page we never asked for. Quick Sync is unaffected — it clears the user first.
- **Quota-safe writes (v9.4)**: bulk inserts on `posts` go through `bulkPutSafe()` from [src/core/quota-manager.ts](../../src/core/quota-manager.ts). On `QuotaExceededError` (or `AbortError` whose `.inner` resolves to one), `evictOldestNonCurrentUser(db, currentUserId)` deletes the least-recently-synced non-current user's posts/piestats and the bulk write retries once. The current user's data is never evicted. Writes inside `db.transaction(...)` keep the raw `bulkPut` (e.g. Grass uploads/approvals/notes) — wrapping there would risk `PrematureCommitError`.
- **Persistent storage opt-in (v9.4)**: After the first successful Quick/Full sync completion, `requestPersistence()` calls `navigator.storage.persist()` (idempotent via the `di.persist.requested` localStorage flag). Lifts Safari ITP eviction and Chrome heuristic eviction risk for users who actually engaged with the dashboard.

## Grass first on a profile page (v9.12, decision G-7)
Grass and the report share one rate limiter (6 req/s), so a report sync started while Grass is still fetching slows both. `GrassLoadGate` ([src/core/grass-load-gate.ts](../../src/core/grass-load-gate.ts)) is on while the *current* Grass view loads: `updateView` turns it on with the spinner and off in `finally` only if it is still the current run (a superseded run keeps filling the cache without holding the button). While it is on, a 📊 click shows a toast and starts neither the sync nor the dashboard; past 400 ms of loading the button also shows as waiting (`di-grass-locked`, `aria-disabled`). The hover preview, the ≤`MAX_PREVIEW_ONLY_UPLOADS` pinned-preview click and anything already running are not held. The reverse (changing the Grass year while a sync runs) still overlaps.

## Tag Analytics Sync (TagAnalyticsApp)
- **Cache-First**: Load from `tag_analytics` table, check 24h expiry + post count diff
- **Delta Sync**: Fetch first 100 posts to detect changes; if diff ≥ threshold (50), fetch delta and re-aggregate
- **Full Sync**: For new tags, fetch all posts and aggregate by user
- **Small Tag Optimization**: Tags with ≤1200 posts (`MAX_OPTIMIZED_POSTS`) are fetched entirely into memory — history, rankings, and milestones calculated locally without DB storage.
